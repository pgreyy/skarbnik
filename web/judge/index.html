Judge guide

Check it in ten minutes

Check Skarbnik yourself: do something, expect a result, verify it against the chain, not against this page. Level A needs only a browser (5 to 10 minutes, no install). Level B is optional and reproduces things on your machine. The same guide is on the site: https://skarbnik.xyz/#/judge

Everything runs on NEAR testnet, contract kintsugi-l2-cihdp.testnet. On private bounties, researchers and the public never see the secret input. Demo bounties use a public input so anyone can check them.

5 to 10 minutes. A browser and the explorer. No install.

Level A: evidence tour

Level A: evidence tour (5 to 10 minutes, no install)

Each step: Do, Expect, Verify, then What this proves and What it does not prove. Transaction links open the testnet explorer.

11 min

Find the contract

Do

open https://testnet.nearblocks.io/address/kintsugi-l2-cihdp.testnet

Expect

a testnet account with a deployed contract and a code hash.

Verify

the code hash equals the one the site reads live on https://skarbnik.xyz/#/evidence/contract

What this proves

the contract the documents name is deployed on testnet, and the site reads that contract.

What it does not prove

that the deployed code is built from this repository; the contract build is not reproducible yet.

23 min

See both sides work: bounty 24 (an AI agent) and bounty 32 (the vendor, with no human)

Do

open bounty 24's three calls in order: commit 4G48c6wa…, reveal 3rBVkucS…, proof 9nAK8gi2…. Then bounty 32's reveal HCjck1DL… and proof 9B7FPyju….

Expect

on bounty 24, a commit holding only a fingerprint, a reveal that publishes the patch, then a submit_groth16 call that pays 0.11 NEAR (the 0.1 NEAR reward and the agent's own 0.01 NEAR fee back). On bounty 32, a submit_groth16 sent by the vendor's prover account 17 minutes after the reveal, with no human between them.

Verify

https://skarbnik.xyz/#/bounties/24 shows "Proof verified" and "Private secret"; the program (data/smooth/) is public, its secret input and reference fix are not in the repository (docs/EVIDENCE.md, "Bounty 24", including how it was checked that the agent could not see the reference fix). https://skarbnik.xyz/#/bounties/32 shows "Proof verified"; the vendor's watch log, with each step's time, the rented GPU and its cost, is in docs/EVIDENCE.md, "The vendor tool".

What this proves

the contract paid each attempt only after checking a Groth16 proof that says PASS for that patch, under the published checker; and the vendor side (prove on a rented GPU, wrap, submit) runs on its own.

What it does not prove

that the patch is secure beyond this checker's tests; that nothing could have read the private folder (bounty 24's agent ran on the same machine, as the same user); more than a few runs; bounty 32 uses the public demo program, so its fix was known.

32 min

Compare with bounties 16 and 17

Do

open bounty 16's proof 5NH9rhRM… and bounty 17's claim BLcWs7dp….

Expect

bounty 16 paid by a proof on the public demo bug; bounty 17 paid by claim_timeout, with no submit_groth16 for its attempt.

Verify

https://skarbnik.xyz/#/bounties/17 says "Timeout settlement" and "Why this is not “Proof verified”": the laptop proof was too slow for the 4 hour window. Bounty 24 was the same kind of task, proven on a GPU instead.

What this proves

proof-checked and timeout payouts are kept apart, and a silent vendor does not block payment.

What it does not prove

that bounty 17's fix passed; the timeout pays without any verdict.

42 min

See a proof pay and a proof fail on the same bounty

Do

open bounty 1's PASS CczggiUN… and FAIL 6B9ocDas….

Expect

two submit_groth16 calls of about 36 Tgas; only the PASS moves NEAR.

Verify

they are different attempts on the same bounty.

What this proves

the contract applies the verdict inside the proof: a PASS pays, a FAIL spends the attempt.

What it does not prove

that every forged proof is refused; the attacks tried are listed in docs/SECURITY.md.

51 min

Compare the checker id

Do

read the allowlist with any view call to get_allowed_image_ids (or docs/TRY_IT.md, step 2).

Expect

exactly one id, dd6c5f42c117ce3a842dbde60cd3fd9f255c85e322317e6bff2357b20533a2fc.

Verify

it equals the image id inside bounty 24's proof (the site's Checker tab; Level B rebuilds it from source).

What this proves

new bounties can only use this one checker, and bounty 24 was decided by it.

What it does not prove

that the id is built from this source (B5 shows that) or that the checker has no bugs.

61 min

Read what is not claimed

Do

open https://skarbnik.xyz/#/evidence/limits or the README's "Trust assumptions" (every limit: docs/CLAIMS.md, "Known limits").

Expect

plain limits, among them: no external audit (only AI review passes), a full access key kept on purpose on the testnet contract (an experimental contract; the mainnet contract is planned without one), testnet only.

Verify

the access key with a view_access_key_list call on kintsugi-l2-cihdp.testnet, and the live code hash against the last deploy in docs/EVIDENCE.md, "Contract code and every deploy".

What this proves

the limits are published, and the full access key can be seen on chain.

What it does not prove

that the list is complete; no one outside the project has audited the contract.

Level B: reproduce

Level B: reproduce (optional)

Commands run from the root of a clone of the repository. The judge bounties for B2 and B3 are 27 to 31 (K = 2, at most 1 attempt per account, 41 h verdict window); 18 to 22 are retired. What each step needs:

B1

Read bounties and the allowlist from the chain (docs/TRY_IT.md, steps 1 to 3)

Needs

curl, python3

Download

none

Memory

small

Expect

bounty 7 is Level 2, open and opened by its Proof 0; the allowlist prints MATCH; the judge bounties show opened or closed.

What this proves

the chain holds what the documents say.

What it does not prove

anything about a proof.

B2

Open a closed judge bounty with a real proof from your own account (docs/TRY_IT.md, step 5)

Needs

near-cli-rs 0.30.1, a testnet account from the faucet (free); about 35 Tgas of testnet gas

Download

none

Memory

small

Expect

the return value "opened", a bounty_opened event naming your account, about 35 Tgas.

What this proves

any account can make the contract check a real Groth16 proof on chain.

What it does not prove

anything about attempts; it reuses bounty 17's Proof 0.

B3

See a proof refused at the pairing check itself (docs/TRY_IT.md, step 6)

Needs

the same as B2

Download

none

Memory

small

Expect

"the Groth16 proof does not verify for this bounty's image id and this journal", about 34.9 Tgas.

What this proves

a wrong seal is refused by the pairing check itself, after every cheaper check passed.

What it does not prove

that every other kind of forgery is refused (see the attacks in docs/SECURITY.md).

B4

Run the contract tests: cargo test -p kintsugi-contract (docs/TRY_IT.md, step 8)

Needs

the Rust toolchain (docs/VERSIONS.md)

Download

the contract's crates, about 3 minutes the first time

Memory

about 1.6 GB

Expect

135 passed; 0 failed.

What this proves

the contract's rules behave as the tests say, including bounty 1's two real proofs checked natively.

What it does not prove

behaviour on chain (B2 and B3 show that); the tests were written by the same team.

B5

Rebuild the checker and compare its image id: ./scripts/check_image_id.sh kintsugi-l2-cihdp.testnet 17 (docs/TRY_IT.md, step 9)

Needs

Docker with buildx, RISC Zero's toolchain, about 10 GB of free disk

Download

RISC Zero's guest builder image, 7.46 GB

Memory

a few GB for the build container

Expect

MATCH on the last line.

What this proves

the checker id on chain is built from this source.

What it does not prove

that the checker is free of bugs or that its checks are enough.

B6

Verify a stored proof: cargo build --release -p skarbnik-host, then ./target/release/skarbnik-host verify docs/evidence/receipts/bounty17_proof0_groth16.bin (docs/TRY_IT.md, step 10)

Needs

after B5

Download

none more

Memory

under 1 GB

Expect

VALID, and a journal sha256 equal to bounty 17's proof0_journal_hash on chain.

What this proves

the stored proof verifies on your machine for the published id, and its journal is the one recorded on chain.

What it does not prove

anything about the secret input or about later attempts.

B7

The agent's checks without a model key: ./scripts/agent_dry_run_test.sh

Needs

Rust with the wasm32-unknown-unknown target, agent/config.local.toml from ./scripts/agent_testnet.sh setup (a testnet account)

Download

none

Memory

small

Expect

11 of 11 checks pass, and nothing is sent.

What this proves

the agent refuses a key not limited to commit and reveal, overspending, and a fix that reads files or the environment.

What it does not prove

that a model writes good fixes.

B8

Verify the contract yourself: rebuild it from its commit with cargo near build reproducible-wasm and compare with the code hash on chain (docs/TRY_IT.md, step 11)

Needs

Docker, cargo-near 0.22.0

Download

the build image sourcescan/cargo-near:0.22.0-rust-1.99.1, about 0.5 GB

Memory

about 2 GB

Expect

sha256 ecf697be619d5dc730de58853ae3daa65bff3ac1a23804a1c390663ca059421e, whose base58 form Gx1JfW7GdpD7sgWf2JwvQhQzfrGy5CnMZyTW2bvFBX6u equals the contract's code hash on chain.

What this proves

the code running on chain is built from the published commit c74bd5c, so reading that source is reading the contract.

What it does not prove

that the source is free of bugs, or that the owner will not deploy other code later (the testnet contract keeps its full access key on purpose; every deploy is listed in docs/EVIDENCE.md).

Expected results are written next to each command in docs/TRY_IT.md, with the run that produced them in docs/EVIDENCE.md. No step needs real money or a mainnet wallet.

Do not start a full vendor proof as part of a review: one attempt takes 1.5 to 4 hours on a laptop CPU, and the Groth16 step needs about 7 GiB of memory (docs/numbers.md).
