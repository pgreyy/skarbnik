Judge guide

Check Skarbnik in five minutes.

Everything here is live on NEAR testnet, and every claim can be checked on chain. The first path needs only a browser.

5 minutesCheck a paid bounty30 minutesVerify it yourselfTry itHost a bountyTry itConnect an agent

The same guide is on the site: https://skarbnik.xyz/#/judge . The contract is kintsugi-l2-cihdp.testnet on NEAR testnet. On private bounties, researchers and the public never see the secret input. Demo bounties use a public input so anyone can check them.

Quick

Check a paid bounty

Four steps. Steps 1 to 3 need only a browser; step 4 needs a testnet wallet. Each step says what you should see, what it shows and what it does not show, and links the chain, so you check it there and not on this page.

  1. 1

    Open a bounty paid by proof

    Open bounty 24 on the site. An AI agent fixed a private bug on a program it could not see, and the contract paid it after checking a proof.

    Open bounty 24
    You should see
    "Proof verified" and "Private secret", a 0.1 NEAR reward, and its commit, reveal and proof under Transactions.
    This shows
    a private repair paid by a proof the contract checked. The program (data/smooth/) is public; its secret input and reference fix are not in the repository (docs/EVIDENCE.md, "Bounty 24").
    Does not show
    that the patch is secure beyond this checker's tests, or that nothing could have read the private folder (the agent ran on the same machine, as the same user).
  2. 2

    Read its payment on the explorer

    Open bounty 24's proof transaction on the NEAR explorer.

    Open the proof transaction
    You should see
    one submit_groth16 call to kintsugi-l2-cihdp.testnet of about 36 Tgas, and in it a transfer of 0.11 NEAR to the agent's account kintsugi-agent-d9410f.testnet: the 0.1 NEAR reward plus its own 0.01 NEAR fee back.
    This shows
    the contract checked the proof and paid in the same call, on chain.
    Does not show
    the patch itself. It is public in the reveal, 3rBVkucS….
  3. 3

    Compare with a timeout

    Open bounty 17: the same kind of task, but the vendor's proof finished after the 4 hour window.

    Open bounty 17
    You should see
    "Timeout settlement" and "Why this is not “Proof verified”", a payment by a claim_timeout call (BLcWs7dp…), and no submit_groth16 call for its attempt.
    This shows
    a silent vendor cannot block payment, and a timeout is shown as a timeout, never as a pass.
    Does not show
    that bounty 17's patch passed. No proof was checked for that attempt.
  4. 4

    Try a judge bounty yourself

    Judge bounties 28 to 31 have the same hashes as bounty 17 and were created closed, so anyone can open one with a real proof. Each can be opened once: send bounty 17's stored Proof 0 to one that is still closed (28; use 29, 30 or 31 if 28 is already open). Each judge bounty takes K = 2 attempts, at most 1 per account, with a 41 hour verdict window.

    Need test NEAR? Get free testnet NEAR from the official faucet or near-faucet.io. A faucet can run out; if it does, ask in the NEAR dev Telegram. Or make a testnet account funded by the faucet with near-cli-rs 0.30.1. Then, from a clone of the repository:

    Needs a testnet wallet, about 2 minutes, test NEAR only.

    near account create-account sponsor-by-faucet-service <you>.testnet autogenerate-new-keypair save-to-legacy-keychain network-config testnet create

    near contract call-function as-transaction kintsugi-l2-cihdp.testnet open_with_groth16 file-args docs/evidence/receipts/judge_open_28.json prepaid-gas '300 Tgas' attached-deposit '0 NEAR' sign-as <you>.testnet network-config testnet sign-with-legacy-keychain send

    Open bounty 28
    You should see
    the return value "opened", a bounty_opened event naming your account, and about 35 Tgas burned. Bounty 28's page then shows it open. Sent again, the same call is refused: "bounty is already open".
    This shows
    any account can make the contract check a real Groth16 proof on chain.
    Does not show
    anything about attempts. It reuses bounty 17's Proof 0.

Verify

Verify it yourself

What you need: Linux (on Windows, use WSL), Docker with buildx, an x86 computer, about 8 GB of free memory and about 10 GB of free disk, the Rust toolchain and RISC Zero's toolchain (docs/VERSIONS.md). The first checker build downloads RISC Zero's guest builder image, 7.46 GB: it took 5 min 12 s with that download and 2 min 20 s with the image cached (docs/numbers.md). The on chain steps below (B2, B3) also need a testnet account. Need test NEAR? Get free testnet NEAR from the official faucet or near-faucet.io. A faucet can run out; if it does, ask in the NEAR dev Telegram.

Judges never need to run the expensive proof. A full vendor proof takes 1.5 to 4 hours on a laptop CPU and its Groth16 step needs about 7 GiB of memory; the proofs these steps check are already on chain.

  1. 1

    Get the code

    git clone https://github.com/pgreyy/skarbnik.git && cd skarbnik

    You should see
    a skarbnik folder with README.md, contract/, harness/ and scripts/.
    This shows
    the public source the checker and the contract are built from.
    Does not show
    that this source is what runs on chain. Step 2 shows it for the checker; "Rebuild the contract" below shows it for the contract.
  2. 2

    Rebuild the checker and compare its id

    ./scripts/check_image_id.sh kintsugi-l2-cihdp.testnet 17

    You should see
    the rebuilt id, the published id and bounty 17's id on chain, all dd6c5f42c117ce3a842dbde60cd3fd9f255c85e322317e6bff2357b20533a2fc, then MATCH on the last line.
    This shows
    the checker id on chain, the only one on the contract's allowlist, is built from this source.
    Does not show
    that the checker is free of bugs, or that its checks are enough.
  3. 3

    Run the public tests

    cargo test -p kintsugi-contract

    You should see
    test result: ok. 135 passed; 0 failed. Cargo downloads the contract's crates first, about 3 minutes.
    This shows
    the contract's rules behave as the tests say, including bounty 1's two real proofs checked natively.
    Does not show
    behaviour on chain (the Quick steps show that), and the tests were written by the same team.
Something failed?
  • check_image_id.sh stops during the build: it needs Docker with the buildx plugin, RISC Zero's toolchain (cargo-risczero 3.0.6, docs/VERSIONS.md) and about 10 GB of free disk.
  • It prints not found for bounty 17's id: the testnet RPC did not answer. Run it again, or name another testnet RPC with RPC=<address> ./scripts/check_image_id.sh kintsugi-l2-cihdp.testnet 17.
  • cargo test is slow the first time: it downloads the contract's crates, about 3 minutes.
  • A judge bounty answers "bounty is already open": another judge opened it first. Use 29, 30 or 31.
  • The agent's dry run (B7 below) needs agent/config.local.toml, made by ./scripts/agent_testnet.sh setup with a testnet account.
Rebuild the contract

Rebuild the deployed contract from its commit and compare it with the code on chain. Needs Docker and cargo-near 0.22.0; the build image sourcescan/cargo-near:0.22.0-rust-1.99.1 is about 0.5 GB (docs/TRY_IT.md, step 11).

git checkout c74bd5c820c1ce684f81e3f794a8e3e804b3d2b5

(cd contract && cargo near build reproducible-wasm)

sha256sum target/near/kintsugi_contract/kintsugi_contract.wasm

Expect sha256 ecf697be619d5dc730de58853ae3daa65bff3ac1a23804a1c390663ca059421e, whose base58 form Gx1JfW7GdpD7sgWf2JwvQhQzfrGy5CnMZyTW2bvFBX6u equals the contract's code hash on chain. This shows the code running on chain is built from the published commit c74bd5c. It does not show that the source is free of bugs, or that the owner will not deploy other code later (the testnet contract keeps its full access key on purpose; every deploy is listed in docs/EVIDENCE.md).

More browser checks
  • Find the contract. Open https://testnet.nearblocks.io/address/kintsugi-l2-cihdp.testnet : a testnet account with a deployed contract and the code hash Gx1JfW7GdpD7sgWf2JwvQhQzfrGy5CnMZyTW2bvFBX6u, the same as on the site's Evidence page, Contract tab (https://skarbnik.xyz/#/evidence/contract), read live. Shows: the contract is real, deployed on NEAR testnet, and the site reads it. Does not show: that the code has no bugs; it has not been externally audited.
  • A proof pays and a proof fails on the same bounty. Bounty 1's PASS CczggiUN… and FAIL 6B9ocDas…: two submit_groth16 calls of about 36 Tgas on two attempts; only the PASS pays the agent. Shows: the contract applies the verdict inside the proof. Does not show: that every forged proof is refused (docs/SECURITY.md).
  • Bounty 16, paid by a proof on the public demo bug. Its proof 5NH9rhRM…, next to bounty 17's timeout claim (Quick step 3).
  • Compare the checker id. Read the allowlist with any view call to get_allowed_image_ids (or docs/TRY_IT.md, step 2): exactly one id, dd6c5f42c117ce3a842dbde60cd3fd9f255c85e322317e6bff2357b20533a2fc, the image id inside bounty 24's proof (the site's Evidence page, Proofs tab). Shows: only this one approved checker can open or settle a new bounty, and bounty 24 was decided by it. Does not show: that the id is built from this source (Verify step 2 shows that) or that the checker is free of bugs.
  • Read what is not claimed. https://skarbnik.xyz/#/evidence/limits or the README's "Trust assumptions" (every limit: docs/CLAIMS.md, "Known limits"): fifteen limits in plain words on the site, among them no external audit (only AI review passes), a full access key kept on purpose on the testnet contract, and testnet only. Check the access key with a view_access_key_list call on kintsugi-l2-cihdp.testnet, and the live code hash against the last deploy in docs/EVIDENCE.md, "Contract code and every deploy". Does not show: that no other limits exist.

Limits

The limits, in short

The short list. Every limit, in plain words, is on the Evidence page.

  • Testnet only. No mainnet contract exists.
  • Small programs only: crash bugs in small WebAssembly modules, with a patch inside each bounty's size limit (1,024 bytes on the open bounties).
  • A working fix is needed: the vendor must already have a reference fix, and its Proof 0 must pass before the bounty opens.
  • No external audit. The contract was reviewed in AI review passes.
  • The testnet contract keeps its full access key on purpose; removing it is planned for the mainnet contract.
  • Run by the team, not outside customers.

Skarbnik
